### SLIDE 8: 10-MINUTE DIEGETIC CLOCK & TIME BANK ROLLOVER
- **Slide Header**: The Time Bank & Rollover System
- **Subtitle**: Real-Time Urgency with Strategic Progression
- **Layout Concept**:
  - Timeline graphic showing Chapter 1 timer rollover into Chapter 2 and Chapter 3.
- **Slide Copy**:
  - **The 10-Minute World Clock (600s)**:
    - Represents the failing psychic frequency of the 1998 time fracture.
    - Diegetic real-time: continues ticking during inventory checks, case notes inspection, and keypad entry.
    - Pauses *only* during active system pause modal to maintain genuine survival urgency.
  - **The Rollover Time Bank**:
    - Finishing a chapter early does not reset the clock to 10:00 &mdash; all unused seconds are **banked and added** to the next chapter's base 600s!
    - Formula: $T_{\text{next}} = 600 + \max(0, T_{\text{remaining}})$.
  - **Chapter Completion Relief Surge**:
    - Escaping a phase triggers an adrenaline relief surge: $+20\% \times \text{Resolve Multiplier}$ composure restored.
- **Speaker Notes**:
  > "To prevent players from dawdling indefinitely, we implemented a diegetic 10-minute world clock. Crucially, speed and precision are rewarded: every remaining second from Chapter 1 rolls directly into Chapter 2's time bank. This persistent temporal momentum creates an addictive, high-stakes pace."

### SLIDE 11: DECLARATIVE LOGIC IN GAMES: THE PROLOG KB
- **Slide Header**: Declarative Game Logic: `spirit_labyrinth.pl`
- **Subtitle**: Replacing Imperative State with Relational Rules
- **Layout Concept**:
  - Code snippet showcase on dark IDE background highlighting actual Prolog rules from the codebase.
- **Slide Copy**:
  - **Dynamic Predicate Assertions**:
    - Locations, doors, items, and taboos are managed via dynamic facts:
      ```prolog
      :- dynamic current_location/1, player_has/1, door_state/2.
      ```
  - **Declarative Puzzle Invariants**:
    - Descent into the well is impossible until all three environmental preconditions are satisfied:
      ```prolog
      well_descent_ready :-
          well_roots_severed,
          well_pulley_rigged,
          well_rope_rigged.
      ```
  - **Backtracking & Unification**:
    - Automated path validation, item eligibility checks, and deduplication through first-order logic queries.
- **Speaker Notes**:
  > "Why Prolog? In traditional game development, verifying complex preconditions across branching chapters leads to fragile nested if-statements. In Prolog, game rules are expressed as declarative invariants. If a player tries to descend the well, the engine unifies `well_descent_ready` against severed roots, mounted pulleys, and threaded ropes. The logic is self-documenting and mathematically provable."

### SLIDE 12: STATE SYNCHRONIZATION & DUAL-STORE RESILIENCE
- **Slide Header**: Dual-Store State Synchronization
- **Subtitle**: Preventing State Desynchronization Across Chapters
- **Layout Concept**:
  - Data flow diagram showing bidirectional sync between `LocalStorage`, `useGameStore`, and `PrologBridge`.
- **Slide Copy**:
  - **The Synchronization Challenge**:
    - Keeping client-side React re-renders, LocalStorage saves, and Prolog's dynamic memory perfectly synchronized across restarts, browser refreshes, and chapter transitions.
  - **The Solution &mdash; Unified Reset & Rollover Routines**:
    - **Atomic Prolog Reset**: Comprehensive `retractall` cascades wiping dynamic predicates on new runs.
    - **Dual-Key Persistence**: Storing active runtime state (`spirits_labyrinth_active_save`) alongside persistent chapter unlocks (`spirits_labyrinth_progress_v1`).
    - **Fail-Safe Fallbacks**: React state auto-recovers missing Prolog facts on mount, ensuring zero progression locking.
- **Speaker Notes**:
  > "A major technical challenge was ensuring state integrity. When a player completes Chapter 2 or restarts from Chapter 1, memory must be purged without leaking lingering flags like unlocked gates or looted items. We engineered unified reset routines that execute atomic `retractall` calls in Prolog while sanitizing LocalStorage and React context simultaneously."

### SLIDE 15: ENGINEERING CHALLENGES & PROBLEM SOLVING
- **Slide Header**: Engineering Challenges & Solutions
- **Subtitle**: Debugging State Pollution, Gate Desync, and Time Rollover
- **Layout Concept**:
  - Before vs. After comparison table of 3 critical technical hurdles overcome during development.
- **Slide Copy**:
  - **Challenge 1: State Pollution Across Chapter Restarts**:
    - *Problem*: Restarting Chapter 1 left Chapter 2/3 dynamic predicates active in memory, breaking puzzle gating.
    - *Fix*: Comprehensive reset routine executing explicit `retractall` for every dynamic predicate across all chapters.
  - **Challenge 2: Gate Desynchronization & Hotspot Blocking**:
    - *Problem*: Hotspots in the exterior courtyard were unreachable due to desynchronized phase location flags.
    - *Fix*: Centralized authoritative location dispatcher in `GameProgressContext` and synchronized Prolog traversal rules.
  - **Challenge 3: Seamless End-Game Progression**:
    - *Problem*: Completing Chapter 3 improperly advertised a non-existent 'Chapter 4 Unlocked'.
    - *Fix*: Adapted transition modal for final-chapter status (`isFinalChapter`), clean exit routing, and a dedicated 'Thanks for Playing' completion banner.
- **Speaker Notes**:
  > "Engineering a complex hybrid system revealed subtle synchronization challenges. For example, ensuring that restarting Chapter 1 purged all Chapter 3 well-rigging predicates required auditing every dynamic assertion in Prolog. Resolving these desynchronization bugs hardened our architecture into a production-grade, fault-tolerant state machine."
